name: refactor description: 마틴 파울러의 방법론에 기반한 체계적인 코드 리팩터링. 사용자가 코드 리팩터링, 코드 구조 개선, 기술 부채 감소, 레거시 코드 정리, 코드 스멜 제거, 또는 코드 유지보수성 향상을 요청할 때 사용합니다. 이 스킬은 연구, 계획, 안전하고 점진적인 구현을 포함하는 단계별 접근 방식을 안내합니다.

코드 리팩터링 스킬

마틴 파울러의 Refactoring: Improving the Design of Existing Code (2nd Edition)에 기반한 코드 리팩터링에 대한 체계적인 접근 방식입니다. 이 스킬은 테스트를 통해 뒷받침되는 안전하고 점진적인 변경을 강조합니다.

"리팩터링은 코드의 외부 동작을 변경하지 않으면서 내부 구조를 개선하는 소프트웨어 시스템 변경 과정입니다." — 마틴 파울러

핵심 원칙

  1. 행동 보존: 외부 동작은 변경되지 않아야 합니다.
  2. 작은 단계: 작고 테스트 가능한 변경을 수행합니다.
  3. 테스트 주도: 테스트는 안전망입니다.
  4. 지속적: 리팩터링은 일회성 이벤트가 아니라 지속적인 과정입니다.
  5. 협업: 각 단계에서 사용자 승인이 필요합니다.

워크플로 개요

1단계: 연구 및 분석

2단계: 테스트 커버리지 평가
    ↓
3단계: 코드 스멜 식별

    ↓

1단계: 연구 및 분석

목표

  • 코드베이스 구조와 목적을 이해합니다.
  • 리팩터링 범위를 식별합니다.
  • 비즈니스 요구사항에 대한 맥락을 수집합니다.

사용자에게 질문할 사항

시작하기 전에 다음 사항을 명확히 합니다.

  1. 범위: 어떤 파일/모듈/함수가 리팩터링되어야 합니까?
  2. 목표: 어떤 문제를 해결하려고 합니까? (가독성, 성능, 유지보수성)
  3. 제약 사항: 변경해서는 안 되는 영역이 있습니까?
  4. 일정 압박: 이것이 다른 작업을 방해하고 있습니까?
  5. 테스트 상태: 테스트가 존재합니까? 통과하고 있습니까?

조치

  • [ ] 대상 코드를 읽고 이해합니다.
  • [ ] 의존성 및 통합을 식별합니다.
  • [ ] 현재 아키텍처를 문서화합니다.
  • [ ] 기존 기술 부채 마커(TODO, FIXME)를 기록합니다.

결과

사용자에게 발견 사항을 제시합니다. - 코드 구조 요약 - 식별된 문제 영역 - 초기 권장 사항 - 진행 승인 요청

2단계: 테스트 커버리지 평가

테스트가 중요한 이유

"테스트 없는 리팩터링은 안전벨트 없이 운전하는 것과 같습니다." — 마틴 파울러

테스트는 안전한 리팩터링의 핵심 동력입니다. 테스트 없이는 버그를 유발할 위험이 있습니다.

평가 단계

  1. 기존 테스트 확인 bash # Look for test files find . -name "*test*" -o -name "*spec*" | head -20

  2. 기존 테스트 실행 ```bash # JavaScript/TypeScript npm test

    Python

    pytest -v

    Java

    mvn test ```

  3. 커버리지 확인 (사용 가능한 경우) ```bash # JavaScript npm run test:coverage

    Python

    pytest --cov=. ```

결정 시점: 사용자에게 문의

테스트가 존재하고 통과하는 경우: - 3단계로 진행합니다.

테스트가 없거나 불완전한 경우: 옵션을 제시합니다. 1. 먼저 테스트를 작성합니다 (권장). 2. 리팩터링 중에 점진적으로 테스트를 추가합니다. 3. 테스트 없이 진행합니다 (위험함 - 사용자 인지 필요).

테스트가 실패하는 경우: - 중단합니다. 리팩터링 전에 실패하는 테스트를 수정합니다. - 사용자에게 문의: 먼저 테스트를 수정해야 할까요?

테스트 작성 가이드라인 (필요한 경우)

리팩터링되는 각 함수에 대해 다음을 커버하는 테스트를 확보합니다. - 정상 경로 (정상 작동) - 엣지 케이스 (빈 입력, null, 경계) - 오류 시나리오 (유효하지 않은 입력, 예외)

"레드-그린-리팩터링" 사이클을 사용합니다. 1. 실패하는 테스트 작성 (빨강) 2. 통과하도록 만듦 (초록) 3. 리팩터링

3단계: 코드 스멜 식별

코드 스멜이란?

코드 내 깊은 문제의 징후입니다. 버그는 아니지만 코드를 개선할 수 있다는 지표입니다.

확인할 일반적인 코드 스멜

전체 목록은 references/code-smells.md를 참조하십시오.

빠른 참조

스멜 징후 영향
긴 메서드 메서드 30-50줄 초과 이해, 테스트, 유지보수 어려움
중복 코드 여러 곳에 동일한 로직 여러 곳에서 버그 수정 필요
큰 클래스 너무 많은 책임을 가진 클래스 단일 책임 원칙 위반
피처 엔비 메서드가 다른 클래스의 데이터를 더 많이 사용 낮은 캡슐화
원시 타입 강박 객체 대신 원시 타입 과다 사용 도메인 개념 누락
긴 매개변수 목록 매개변수 4개 이상인 메서드 올바른 호출 어려움
데이터 덩어리 동일한 데이터 항목이 함께 나타남 추상화 누락
스위치 문 복잡한 switch/if-else 체인 확장 어려움
투기적 일반화 "혹시 몰라서" 작성된 코드 불필요한 복잡성
죽은 코드 사용되지 않는 코드 혼란, 유지보수 부담

분석 단계

  1. 자동화된 분석 (스크립트 사용 가능한 경우) bash python scripts/detect-smells.py <file>

  2. 수동 검토

    • 코드를 체계적으로 검토합니다.
    • 위치 및 심각도를 포함하여 각 스멜을 기록합니다.
    • 영향별로 분류합니다 (치명적/높음/중간/낮음).

  3. 우선순위 지정 다음 스멜에 집중합니다.

    • 현재 개발을 방해하는 것
    • 버그나 혼란을 유발하는 것
    • 가장 많이 변경되는 코드 경로에 영향을 미치는 것

결과: 스멜 보고서

사용자에게 제시합니다. - 식별된 스멜 목록 및 위치 - 각 스멜에 대한 심각도 평가 - 권장 우선순위 - 우선순위 승인 요청

4단계: 리팩터링 계획 수립

리팩터링 선택

각 스멜에 대해 카탈로그에서 적절한 리팩터링을 선택합니다.

전체 목록은 references/refactoring-catalog.md를 참조하십시오.

스멜-리팩터링 매핑

코드 스멜 권장 리팩터링
긴 메서드 메서드 추출, 임시 변수를 쿼리로 바꾸기
중복 코드 메서드 추출, 메서드 상향, 템플릿 메서드 형성
큰 클래스 클래스 추출, 서브클래스 추출
피처 엔비 메서드 이동, 필드 이동
원시 타입 강박 원시 타입을 객체로 바꾸기, 타입 코드를 클래스로 바꾸기
긴 매개변수 목록 매개변수 객체 도입, 전체 객체 유지
데이터 덩어리 클래스 추출, 매개변수 객체 도입
스위치 문 조건문을 다형성으로 바꾸기
투기적 일반화 계층 축소, 클래스 인라인화, 죽은 코드 제거
죽은 코드 죽은 코드 제거

계획 구조

templates/refactoring-plan.md의 템플릿을 사용합니다.

각 리팩터링에 대해: 1. 대상: 어떤 코드가 변경될 것인가 2. 스멜: 어떤 문제를 해결하는가 3. 리팩터링: 어떤 기법을 적용할 것인가 4. 단계: 상세한 마이크로 단계 5. 위험: 무엇이 잘못될 수 있는가 6. 롤백: 필요한 경우 어떻게 되돌릴 것인가

단계별 접근 방식

중요: 리팩터링을 단계적으로 점진적으로 도입합니다.

A단계: 빠른 성과 (낮은 위험, 높은 가치) - 명확성을 위해 변수 이름 변경 - 명백한 중복 코드 추출 - 죽은 코드 제거

B단계: 구조적 개선 (중간 위험) - 긴 함수에서 메서드 추출 - 매개변수 객체 도입 - 적절한 클래스로 메서드 이동

C단계: 아키텍처 변경 (높은 위험) - 조건문을 다형성으로 바꾸기 - 클래스 추출 - 디자인 패턴 도입

결정 시점: 사용자에게 계획 제시

구현 전에: - 전체 리팩터링 계획을 보여줍니다. - 각 단계와 위험을 설명합니다. - 각 단계에 대한 명시적 승인을 받습니다. - 질문: "A단계로 진행해도 될까요?"

5단계: 점진적 구현

황금률

"변경 → 테스트 → 통과? → 커밋 → 다음 단계"

구현 리듬

각 리팩터링 단계에 대해:

  1. 사전 확인

    • 테스트가 통과하고 있는지 (초록)
    • 코드가 컴파일되는지

  2. 하나의 작은 변경 수행

    • 카탈로그의 메커니즘을 따릅니다.
    • 변경 사항을 최소한으로 유지합니다.

  3. 검증

    • 즉시 테스트를 실행합니다.
    • 컴파일 오류를 확인합니다.

  4. 테스트가 통과하는 경우 (초록)

    • 설명적인 메시지로 커밋합니다.
    • 다음 단계로 이동합니다.

  5. 테스트가 실패하는 경우 (빨강)

    • 즉시 중단합니다.
    • 변경 사항을 되돌립니다.
    • 무엇이 잘못되었는지 분석합니다.
    • 불명확한 경우 사용자에게 문의합니다.

커밋 전략

각 커밋은 다음 조건을 충족해야 합니다. - 원자적: 하나의 논리적 변경 - 되돌릴 수 있는: 되돌리기 쉬움 - 설명적인: 명확한 커밋 메시지

커밋 메시지 예시:

refactor: Extract calculateTotal() from processOrder()
refactor: Rename 'x' to 'customerCount' for clarity
refactor: Remove unused validateOldFormat() method

진행 상황 보고

각 하위 단계 후에 사용자에게 보고합니다. - 변경 사항 - 테스트는 여전히 통과하고 있습니까? - 발생한 문제 - 질문: "다음 배치로 계속 진행할까요?"

6단계: 검토 및 반복

리팩터링 후 체크리스트

  • [ ] 모든 테스트 통과
  • [ ] 새로운 경고/오류 없음
  • [ ] 코드 성공적으로 컴파일
  • [ ] 동작 변경 없음 (수동 확인)
  • [ ] 필요한 경우 문서 업데이트
  • [ ] 커밋 기록이 깔끔함

지표 비교

전후 복잡도 분석 실행:

python scripts/analyze-complexity.py <file>

개선 사항 제시: - 코드 줄 변경 - 순환 복잡도 변경 - 유지보수성 지수 변경

사용자 검토

최종 결과 제시: - 모든 변경 사항 요약 - 코드 전/후 비교 - 지표 개선 - 남은 기술 부채 - 질문: "이러한 변경 사항에 만족하십니까?"

다음 단계

사용자와 논의: - 추가로 처리할 스멜이 있습니까? - 후속 리팩터링 일정을 잡을까요? - 다른 곳에도 유사한 변경을 적용할까요?

중요 가이드라인

언제 중단하고 질문해야 하는가

다음 경우 항상 일시 중지하고 사용자에게 문의하십시오. - 비즈니스 로직이 불확실할 때 - 변경이 외부 API에 영향을 미칠 수 있을 때 - 테스트 커버리지가 불충분할 때 - 중요한 아키텍처 결정이 필요할 때 - 위험 수준이 증가할 때 - 예상치 못한 복잡성에 직면할 때

안전 규칙

  1. 테스트 없이 리팩터링하지 마십시오 (사용자가 명시적으로 위험을 인지하지 않는 한)
  2. 큰 변경을 하지 마십시오 - 작은 단계로 나눕니다.
  3. 각 변경 후 테스트 실행을 건너뛰지 마십시오.
  4. 테스트가 실패하면 계속하지 마십시오 - 먼저 수정하거나 롤백하십시오.
  5. 추측하지 마십시오 - 의심스러울 때는 질문하십시오.

하지 말아야 할 것

  • 리팩터링과 기능 추가를 결합하지 마십시오.
  • 프로덕션 비상 상황 중에 리팩터링하지 마십시오.
  • 이해하지 못하는 코드를 리팩터링하지 마십시오.
  • 과도하게 설계하지 마십시오 - 간단하게 유지하십시오.
  • 모든 것을 한 번에 리팩터링하지 마십시오.

시나리오: 중복이 있는 긴 메서드

이전:

function processOrder(order) {
  // 150 lines of code with:
  // - Duplicated validation logic
  // - Inline calculations
  // - Mixed responsibilities
}

리팩터링 단계:

  1. processOrder()에 대한 테스트가 존재하는지 확인
  2. 유효성 검사를 validateOrder()로 추출
  3. 테스트 - 통과해야 함
  4. 계산을 calculateOrderTotal()로 추출
  5. 테스트 - 통과해야 함
  6. 알림을 notifyCustomer()로 추출
  7. 테스트 - 통과해야 함
  8. 검토 - processOrder()는 이제 3개의 명확한 함수를 조정함

이후:

function processOrder(order) {
  validateOrder(order);
  const total = calculateOrderTotal(order);
  notifyCustomer(order, total);
  return { order, total };
}
