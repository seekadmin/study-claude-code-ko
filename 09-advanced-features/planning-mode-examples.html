User: /plan 블로그용 REST API 만들어줘

Claude: 블로그 API에 대한 전체 계획을 작성하겠습니다.

## 블로그 REST API 구현 계획

### 1단계: 프로젝트 설정 (15분)
1. Node.js + Express 프로젝트 초기화
2. TypeScript 설정 구성
3. 의존성 설치 (express, pg, jwt, joi)
4. 환경 변수 설정
5. 프로젝트 구조 구성

### 2단계: 데이터베이스 계층 (30분)
6. DB 스키마 설계
   - users 테이블 (id, email, password_hash, created_at)
   - posts 테이블 (id, user_id, title, content, published, created_at, updated_at)
   - comments 테이블 (id, post_id, user_id, content, created_at)
7. 마이그레이션 파일 생성
8. DB 연결 풀 구성
9. 모델 구현

### 3단계: 인증 (45분)
10. 회원가입 API
11. 로그인 API (JWT)
12. 인증 미들웨어
13. bcrypt 비밀번호 해싱
14. 토큰 갱신 로직

### 4단계: 게시글 API (40분)
15. GET /api/posts (페이지네이션)
16. GET /api/posts/:id
17. POST /api/posts (인증 필요)
18. PUT /api/posts/:id (권한 체크)
19. DELETE /api/posts/:id
20. GET /api/users/:id/posts

### 5단계: 댓글 API (30분)
21. 댓글 조회
22. 댓글 생성
23. 댓글 삭제

### 6단계: 검증 및 에러 처리 (30분)
24. Joi 검증
25. 글로벌 에러 핸들러
26. 입력 sanitization
27. rate limiting

### 7단계: 테스트 (60분)
28. 단위 테스트
29. 통합 테스트 (auth)
30. 통합 테스트 (posts)
31. 통합 테스트 (comments)
32. 테스트 커버리지 80%+

### 8단계: 문서 및 배포 (30분)
33. Swagger 문서 생성
34. README 작성
35. Docker 설정
36. CI/CD 구성

**예상 시간**: 4.5시간
**생성 파일 수**: 약 25개
**핵심 기술**: Express, PostgreSQL, JWT, TypeScript

**API 요약**:
- 인증: 2개
- 게시글: 6개
- 댓글: 3개
- 총 11개 엔드포인트

예제 2: 데이터베이스 마이그레이션

계획 모드 사용

## MongoDB → PostgreSQL 마이그레이션 계획

### 1단계: 분석 및 준비 (Day 1)
1. 기존 MongoDB 스키마 분석
2. 데이터 관계 및 구조 파악
3. 데이터 규모 및 성장률 분석
4. PostgreSQL 스키마 설계
5. 데이터 타입 매핑 정의
6. 마이그레이션 리스크 분석

### 2단계: PostgreSQL 구성 (Day 1)
7. DB 설치 및 설정
8. 테이블/인덱스/제약조건 생성
9. 커넥션 풀 설정
10. 백업 전략 구성

### 3단계: Dual-write 구현 (Day 2~3)
11. DB 추상화 계층 생성
12. MongoDB + PostgreSQL 동시 쓰기
13. 데이터 일관성 검증 로직
14. 스테이징 환경 테스트
15. 모니터링 구성

### 4단계: 데이터 마이그레이션 (Day 4)
16. MongoDB export 스크립트
17. PostgreSQL import 스크립트
18. 데이터 변환 로직
19. 테스트 데이터 마이그레이션
20. 무결성 검증

### 5단계: 점진적 전환 (Day 5~7)
21. 프로덕션 dual-write 활성화
22. 배치 단위 데이터 이동
23. 실시간 일관성 체크
24. 모니터링 강화
25. 문제 발생 시 롤백 대응

### 6단계: PostgreSQL 전환 (Day 8)
26. 읽기 트래픽 PostgreSQL 전환
27. 성능 분석
28. 쿼리 최적화
29. MongoDB 유지 (안전장치)

### 7단계: MongoDB 종료 (Day 9~10)
30. MongoDB write 중단
31. 2주간 백업 유지
32. 코드 제거
33. 데이터 아카이빙
34. 인프라 제거

**예상 기간**: 10일
**위험도**: 높음
**롤백 전략**: MongoDB 유지 + dual-write 유지
**성공 기준**:
- 데이터 손실 0건
- 성능 저하 5% 미만
- 모든 테스트 통과

**주요 리스크**
- 데이터 불일치
- 성능 저하
- 다운타임
- 데이터 손실

**완화 전략**
- Dual-write
- 단계적 전환
- 실시간 모니터링
- 빠른 롤백

예제 3: 프론트엔드 리팩터링

User: /plan React 앱을 class component에서 hooks로 리팩터링해줘

Claude: 체계적인 리팩터링 계획을 수립하겠습니다.

## React Class → Hooks 마이그레이션 계획

### 1단계: 준비 및 분석 (2시간)
1. 모든 class component 감사 (전체 .jsx/.tsx 파일 탐색)
2. 복잡도 기준 분류:
   - 단순 (state만 사용): 약 15개 컴포넌트
   - 중간 (lifecycle 포함): 약 23개 컴포넌트
   - 복잡 (여러 lifecycle + refs): 약 8개 컴포넌트
3. 외부 라이브러리 의존성 확인
4. 컴포넌트 의존성 그래프 생성
5. 마이그레이션 순서 결정 (leaf node 우선)

### 2단계: 환경 설정 (1시간)
6. React v18+ 업그레이드
7. ESLint hooks 규칙 적용
8. 변환 템플릿 생성
9. 테스트 환경 구성
10. 시작 전 체크포인트 생성

### 3단계: 단순 컴포넌트 마이그레이션 (4시간)
11. 단순 state 컴포넌트 변환 (15개)
12. this.state → useState 변경
13. this.setState → setter 함수 변경
14. 각 컴포넌트 테스트
15. 테스트 코드 업데이트

### 4단계: 중간 컴포넌트 마이그레이션 (8시간)
16. lifecycle 포함 컴포넌트 변환 (23개)
17. componentDidMount → useEffect
18. componentDidUpdate → useEffect
19. componentWillUnmount → cleanup 함수
20. 전체 테스트 수행

### 5단계: 복잡 컴포넌트 마이그레이션 (12시간)
21. 복잡 컴포넌트 변환 (8개)
22. useRef 적용
23. 공통 로직 custom hook으로 분리
24. edge case 처리
25. 집중 테스트

### 6단계: 공통 로직 추출 (6시간)
26. 중복 로직 분석
27. custom hooks 생성:
   - useAuth
   - useFetch
   - useLocalStorage
   - useDebounce
28. 컴포넌트 리팩터링
29. hook 단위 테스트

### 7단계: 성능 최적화 (4시간)
30. React.memo 적용
31. useCallback 최적화
32. useMemo 적용
33. 성능 프로파일링 및 개선

### 8단계: 정리 및 문서화 (2시간)
34. 불필요한 class 유틸 제거
35. 문서 업데이트
36. 코딩 가이드 수정
37. 마이그레이션 가이드 작성

**예상 시간**: 5일 (39시간)
**수정 파일 수**: 46개 컴포넌트
**리스크 수준**: 중간

**마이그레이션 순서**
1. 의존성 없는 leaf 컴포넌트
2. 중간 레벨 컴포넌트
3. 상위 container 컴포넌트
4. App.jsx (마지막)

**테스트 전략**
- 각 컴포넌트 단위 테스트
- 사용자 플로우 통합 테스트
- 시각적 회귀 테스트
- 성능 벤치마크

**성공 기준**
- 모든 테스트 통과
- UI 변경 없음
- 성능 유지 또는 개선
- 번들 크기 증가 없음

예제 4: 보안 구현(Security Implementation)

## 웹 애플리케이션 보안 구현 계획

### 1단계: 보안 감사 (Day 1)
1. 자동 보안 스캐너 실행 (npm audit, Snyk)
2. 의존성 취약점 점검
3. OWASP Top 10 준수 여부 확인
4. 인증 흐름 감사
5. 데이터 처리 방식 검토
6. 보안 취약점 문서화

### 2단계: 인증 강화 (Day 2~3)
7. 강력한 비밀번호 정책 적용
8. 비밀번호 강도 체크 추가
9. 로그인 rate limiting 적용
10. 로그인 실패 시 계정 잠금
11. 2FA (TOTP) 구현
12. 세션 관리 개선
13. 안전한 비밀번호 재설정 흐름 구현

### 3단계: 권한 관리 (Day 3~4)
14. RBAC(Role-Based Access Control) 구현
15. 모든 API에 권한 체크 추가
16. 최소 권한 원칙 적용
17. 감사 로그 추가
18. 리소스 단위 권한 제어

### 4단계: 데이터 보호 (Day 4~5)
19. 민감 데이터 암호화
20. 모든 통신 TLS 적용
21. 세션 저장 보안 강화
22. 로그에서 PII 마스킹
23. 데이터 보관 정책 적용
24. 파일 업로드 보안 처리

### 5단계: 입력 검증 (Day 5~6)
25. 모든 API 입력 검증
26. XSS 방지 (CSP 적용)
27. SQL Injection 방지 (prepared statement)
28. CSRF 보호
29. 요청 크기 제한
30. 파일 타입 검증

### 6단계: 보안 헤더 (Day 6)
31. 보안 헤더 추가:
   - HSTS
   - X-Content-Type-Options
   - X-Frame-Options
   - CSP
32. CORS 설정 강화
33. 불필요한 HTTP method 제거

핵심 요약

계획 모드의 장점

  1. 명확성: 작업 시작 전에 명확한 로드맵을 수립
  2. 예측 가능성: 시간과 노력에 대한 예상 제공
  3. 위험 평가: 잠재적인 문제를 조기에 식별
  4. 우선순위 설정: 작업을 논리적인 순서로 구성
  5. 승인 절차: 실행 전에 검토 및 승인 가능
  6. 수정 용이성: 피드백을 반영하여 계획 조정 가능

계획 모드를 사용해야 하는 경우

✅ 항상 사용하는 것이 좋은 경우: - 며칠 이상 소요되는 프로젝트 - 팀 협업 - 중요한 시스템 변경 - 새로운 개념 학습 - 복잡한 리팩터링

❌ 사용하지 않아도 되는 경우: - 버그 수정 - 작은 변경 사항 - 단순한 질의 - 간단한 실험
